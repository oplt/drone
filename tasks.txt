# Drone App audit and implementation roadmap

Audit date: 2026-08-12

Scope: the current dirty working tree, with emphasis on the Agriculture product journey, Video Analysis, and Vision Training. This document is the deliverable requested by `prompt.txt`; no production feature code was changed during the audit.

## Executive summary

The repository contains most of the ingredients for a strong evidence-first agriculture product: fields and missions, live telemetry, a video catalog, a mature video detector path, a custom-model training pipeline, geospatial observations, review workflows, reports, and action records. The main issue is not a lack of features. It is that the core vertical slice is not connected reliably.

The current Agriculture post-flight action requests seven analysis names by default. The Agriculture API then requires a separately registered and deployed `AgricultureModelVersion` for almost all of them, while the Vision Training module deploys a different `ModelVersion` type and the Agriculture service does not start a `VideoAnalysisJob`. It only consumes detections that already happen to exist for the mission. This means the intended FIELD -> MISSION -> CAPTURE -> ANALYZE -> FINDINGS journey can fail before useful work starts or can aggregate an empty, unrelated result. Capability aliases such as `canopy`/`canopy_cover` and `rows`/`row_detection` make the contract even less deterministic.

Three confirmed runtime defects make this a release blocker independently of the product-flow gap: Agriculture routes reference `settings` without importing it, field-zone creation references `new_id()` without importing it, and observation aggregation calls SQLAlchemy `in_()` with two positional values instead of one iterable. The latter was reproduced directly and raises `TypeError` when analysis reaches model lookup.

The highest-value sequence is therefore:

1. Restore executable correctness and add route-level regression coverage (`AGR-001`).
2. Define one capability and deployment contract between Vision, Video Analysis, and Agriculture (`ML-001`, `AGR-002`).
3. Make Agriculture analysis an idempotent orchestration of video inference and finding aggregation (`VID-001`, `AGR-003`).
4. Protect training data from concurrent overwrites and remove failed-training dead ends (`ML-002`, `ML-003`).
5. Replace raw configuration and duplicated technical workspaces with a map-first, stage-aware farmer journey (`UX-001`, `UX-002`).
6. Establish production telemetry before tuning inference, SAHI, decoding, or tracking (`PERF-001`, then `PERF-002`).

The recommended architecture remains a modular monolith plus isolated Celery/GPU workers. Agriculture should own agronomic intent, findings, review, and actions; Video Analysis should own media inference and evidence; Vision Training should own datasets, runs, evaluations, and immutable model artifacts. Integration should happen through typed application contracts and persisted job links, not cross-module ORM queries or duplicate model registries.

### Current farmer/agronomist journey

1. Create a field using text metadata and raw boundary GeoJSON.
2. Open a field and configure a mission with raw takeoff/landing longitude and latitude, raw exclusion-zone JSON, and waypoint limits.
3. Run preflight and flight controls in a large live-status panel.
4. Register or upload video/media through one of several media surfaces.
5. Start Agriculture post-flight analysis, which hardcodes a broad capability set.
6. Separately configure or run Video Analysis if detections are needed.
7. Separately train and deploy a custom Vision model, which does not satisfy the Agriculture deployment gate.
8. Review findings across the flight page and a separate analysis page, with overlapping report, review, model, evidence, and governance controls.
9. Create actions or exports after navigating technical tables, JSON-oriented controls, and internal terminology.

The journey exposes implementation boundaries instead of user intent. A farmer should primarily answer: Which field? What should the flight inspect? Is the capture usable? What changed? Where should I scout? What action should I approve? Model versions, detector types, slice overlap, telemetry tolerances, and raw GeoJSON should be progressive-disclosure controls for specialists.

## Recommended architecture

### Decision: modular monolith with explicit feature contracts

Keep the existing deployable shape while replacing cross-module ORM access with three ownership boundaries:

- Agriculture owns fields, mission intent, agronomic capabilities, observations/findings, human review, action recommendations, exports, and agronomic release policy.
- Video Analysis owns video assets, inference jobs, frame/detection evidence, telemetry association metadata, tracking, summaries, and evidence retention requests.
- Vision Training owns projects, source media ingestion, dataset snapshots, annotations, splits, training/evaluation runs, artifacts, and immutable `ModelVersion` records.
- A capability release record links an Agriculture capability to a deployed Vision `ModelVersion` and its supported Video inference contract. It should not copy artifact URIs, hashes, metrics, or lifecycle state.
- Agriculture creates a persisted analysis orchestration with explicit stage/job links. Video completion emits or records an idempotent terminal transition; Agriculture aggregation consumes the completed job through a typed query contract.

Why this option: it preserves the useful modules and current deployment model, establishes one owner per durable fact, supports independent GPU workers, and avoids the operational cost of premature services.

### Alternatives considered

1. Merge Agriculture, Video Analysis, and Vision into one feature module. Rejected: media inference and model lifecycle are reusable platform capabilities, and merging would create a larger coupled domain without fixing ownership.
2. Split the three modules into network services now. Deferred: there is no measured scaling, team-ownership, isolation, or deployment requirement that offsets distributed transactions, versioned RPC contracts, and operational overhead.
3. Keep both model registries synchronized with copy jobs. Rejected: duplicated artifact truth and lifecycle drift are the current problem. Link release policy to the canonical Vision model instead.

Reconsider service extraction only when at least one measured trigger exists: independent release cadence is repeatedly blocked, GPU queue scaling cannot be isolated in the current deployment, a separate team owns the contract, or security/tenancy requires a process boundary.

### Heuristic findings

- Visibility of system status: job statuses exist, but the three modules do not present one stage-aware analysis state. Users can see “completed” without knowing whether findings were aggregated or whether frames silently failed.
- Match with the real world: field and scouting concepts exist, but primary planning still asks for GeoJSON, coordinates, analysis identifiers, and model internals.
- User control: cancellation exists in backend APIs but is missing from the training UI; failed locked datasets have no visible recovery route.
- Consistency: flight and analysis pages duplicate report/review/governance surfaces, while Video Analysis is a disconnected top-level tool.
- Error prevention: the UI requests unavailable analysis capabilities, annotation saves have no revision conflict, and direct API deployment bypasses release thresholds.
- Recognition over recall: prompt dialogs require users to remember reviewer IDs, reason text, and media identifiers.
- Efficiency: 2,000 detection buttons/rows and repeated full invalidation penalize common review and labeling actions.
- Recovery: video failure can leave an asset in `analyzing`; all frame failures can still yield a completed job; restore-drill cleanup currently fails.
- Help: internal labels and raw controls lack field-level guidance and domain examples.

## AGRICULTURE PRODUCT FLOW

### Current flow

`Field list -> field detail -> raw mission plan -> preflight -> live flight/media -> hardcoded post-flight request -> optional separate video inference -> duplicated findings/review pages -> action/export`

### Problems

- Analysis does not own or await the inference work it needs.
- The deployed-model check targets a registry not populated by Vision Training.
- Capability names are inconsistent across UI, gate, service, and model records.
- Quality, canopy, row, stand, weed, water, and health analyses are requested regardless of media/sensor/model availability.
- Primary field setup and planning expose raw geospatial serialization and coordinates.
- The flight workspace combines command, upload, analysis, review, reports, governance, and actions; the analysis workspace duplicates much of it.
- Evidence navigation crosses modules through global browser events and identifiers whose type is not explicit.
- Outputs emphasize detections and implementation statuses instead of prioritized field findings and scout/action decisions.

### Recommended flow

`Fields map/list -> guided field setup -> choose inspection goal -> map-first plan -> preflight/capture -> automatic media registration -> capture-quality gate -> available-capability analysis -> prioritized map findings -> review/assign scout route -> approve/export action -> compare next flight`

Specialist controls remain available behind “Advanced”: exact model release, detector mode, thresholds, SAHI settings, telemetry tolerance, raw mission geometry, and artifact provenance.

### Why

This flow matches the strongest competitor pattern without copying their claims: organize by field, automate the capture-to-result handoff, visualize findings on the field, and end with an operational decision. It also matches this repository’s stated evidence-first and human-approval product principles.

The flow is delivered by `AGR-002`, `AGR-003`, `UX-001`, `UX-002`, `AGR-004`, `EVD-001`, `PROD-001`, and `PROD-002`. Their dependency order is shown later.

| [DJI SmartFarm](https://www.dji.com/ag/smartfarm-web) | Parcel archive, map-centric route and parameter review | Flight records and equipment/operation management around parcels | Team/organization operation is prominent | Device-fleet breadth is not the current differentiator; preserve vendor-neutral media contracts. |

## PERFORMANCE PLAN

### Frontend

- Current bottlenecks: global map/3D providers and chunks, full detection payload polling, thousands of timeline controls/markers, O(N) active-detection scans on time updates, broad query invalidation after annotation edits, and giant components that rerender unrelated regions.
- Measure first: route-level JS/CSS/network transfer, LCP/INP on Agriculture and Video Analysis, React commit count, memory at 1k/10k/100k detections, requests/minute while jobs run and while tabs are hidden.
- Target state: route-only loading for Google Maps/Cesium/3D; delta or cursor fetches instead of repeated full payloads; virtualized/aggregated tables and timelines; map clustering/viewport queries; indexed active-time lookup; narrow query cache updates.
- Tasks: `VID-002`, `FE-001`, `FE-002`, `PERF-001`.

### API

- Current bottlenecks: 2,000-row hard truncation without continuation metadata, repeated large payloads, 10,000-row spatial prefetch, mixed response/error shapes, and synchronous filesystem work inside async Agriculture paths.
- Measure first: p50/p95 latency and response bytes by endpoint; query count; event-loop blocked time; timeout/error rate; payload completeness.
- Target state: explicit cursor/window contracts, compact summaries/aggregates for visualization, typed terminal-stage responses, bounded async-safe file operations, and no silent truncation.
- Tasks: `API-001`, `VID-002`, `AGR-004`, `STOR-001`.

### Database

- Current bottlenecks: Agriculture sorts/limits before Python bbox filtering, reports the sampled row count as total, scans detections then performs linear evidence lookup, and relies on application checks for some active/deployed uniqueness.
- Measure first: `EXPLAIN (ANALYZE, BUFFERS)` for viewport and mission-detection queries at realistic tenant sizes; lock/conflict tests for deploy/start; rows fetched versus rows returned.
- Target state: tenant/mission/time predicates and `ST_Intersects`/bbox execute before limit; useful spatial/composite indexes; exact or explicitly estimated totals; O(D+E) evidence association; database-enforced active/production invariants where possible.
- Tasks: `AGR-004`, `ML-004`, `ML-005`, `AGR-003`.

### Video decoding

- Current behavior: every frame is decoded even when only every Nth timestamp is selected. The synthetic CPU run was fast enough that this cannot be called the dominant production bottleneck without real recordings and storage conditions.
- Measure first: wall time and CPU per input video minute by codec/resolution/storage; seek/keyframe behavior; queue wait; selected/decoded ratio; decode errors.
- Candidate experiments: native decoder stride/seek, ffmpeg/PyAV paths, bounded decode-prefetch, and hardware decode. Promote only if stage telemetry shows meaningful end-to-end improvement and frame/timestamp equivalence tests pass.
- Tasks: `PERF-001`, then `PERF-002`.

### Inference

- Current behavior: standard inference calls the model for one selected frame at a time. Synthetic CPU batching improved throughput only about 8-9%; no GPU conclusion is possible.
- Measure first: queue wait, model load, preprocessing, inference, postprocessing, persistence, GPU utilization/memory, throughput, and p95 latency by model/version/input size.
- Candidate experiments: bounded dynamic batching, warm worker/model lifecycle, half precision where validated, and input-size profiles. Gate on unchanged evaluation thresholds, bounded memory, and better total video turnaround.
- Tasks: `PERF-001`, `PERF-002`, `VID-004`.

### SAHI

- Current behavior: sliced inference is an explicit mode with per-frame slice/merge cost; the active audit environment could not benchmark it.
- Measure first: small-object recall/precision versus standard inference, slices/frame, merge time, total latency, and GPU memory on representative crop imagery.
- Target state: use SAHI only for model/capability profiles whose evaluation proves an accuracy benefit worth the cost. Store the evaluated slice profile in the release contract; do not expose arbitrary defaults as a farmer choice.
- Tasks: `PERF-001`, `PERF-002`, `ML-005`.

### Tracking

- Current behavior: tracking is sequential after detections and writes tracking metadata with every result. UI rendering does not exploit track-level aggregation enough.
- Measure first: tracker time/frame, ID switches/fragmentation on representative flights, track count versus detection count, and payload reduction from track summaries.
- Target state: keep tracking only when it improves evidence review or counts; emit track-level summaries and lazy detection details; avoid persisting redundant raw configuration on every detection.
- Tasks: `VID-002`, `STOR-001`, `PERF-001`.

### Storage

- Current bottlenecks: one crop file per detection, unchecked image writes, local paths in API data, artifact/media writes before transaction commit, duplicated raw JSON, no complete retention/orphan policy, and 1 GB local uploads without checksum-based identity.
- Measure first: bytes per video minute/detection/run, inode/file count, orphan rate, crop hit rate, write failures, backup/restore time, and object-store egress where applicable.
- Target state: content-addressed source identity; storage adapter URLs/IDs rather than local paths; transactional staging/finalization; on-demand or policy-bounded crops; lifecycle/retention jobs; integrity hashes and repair tooling.
- Tasks: `STOR-001`, `SEC-001`, `VID-004`.

## P0 — restore a safe working vertical slice

### AGR-001 — Repair confirmed Agriculture runtime faults and executable coverage

Tags: `P0` `backend` `agriculture` `correctness` `tests`

Problem: Multiple core Agriculture paths can raise before doing useful work. Static imports alone do not exercise the affected module-level names and SQL expression construction.

Evidence:

- `backend/modules/agriculture/api.py` references `settings` throughout media, advisory, telemetry, upload/restore, manifest, analysis, and export routes without importing it.
- `backend/modules/agriculture/field_context.py` calls `new_id()` in zone creation without importing it.
- `backend/modules/agriculture/service.py` calls `AgricultureModelVersion.status.in_("validated", "deployed")`; direct evaluation raises `TypeError: ColumnOperators.in_() takes 2 positional arguments but 3 were given`.
- Focused Ruff reports these undefined names, while current focused tests do not execute all affected branches.

Implementation:

1. Import `settings` from the project’s canonical configuration module and `new_id` from the established ID helper.
2. Change `in_` to receive one iterable and search the touched paths for the same SQLAlchemy misuse.
3. Add application-level tests that execute one representative route from each affected cluster with dependency overrides: media inventory/upload, telemetry/advisory, frame manifest, analysis creation, export, and field-zone creation.
4. Add a service test that reaches model-version lookup and proves the query is constructed and executed.
5. Add focused Ruff `F821` and import checks for Agriculture to CI; do not combine this with the repository-wide formatting backlog.

Files likely affected: `backend/modules/agriculture/api.py`; `backend/modules/agriculture/field_context.py`; `backend/modules/agriculture/service.py`; `backend/tests/modules/agriculture/*`; focused lint configuration or CI workflow.

Acceptance criteria:

- All confirmed undefined-name defects in Agriculture are removed.
- Representative affected endpoints execute beyond configuration/name resolution under tests.
- Model lookup accepts validated/deployed statuses without raising.
- No public response shape or persisted schema changes.

Tests: New route/service regressions; focused Agriculture test suite; Ruff `F821,F401`; mypy on touched files; full backend suite if CI capacity permits.

Performance target: No additional database queries in the repaired paths; model lookup remains one bounded query.

Dependencies: None. This is the first implementation task.

Risk: Low. The main risk is importing a configuration singleton that differs from current dependency-injection conventions; use the same source as adjacent modules.

Size: S.

### ML-001 — Establish one model artifact and capability release contract

Tags: `P0` `architecture` `vision` `agriculture` `model-governance`

Problem: Vision Training deploys `ModelVersion`, while Agriculture gates analysis on a separate `AgricultureModelVersion`. Artifact identity, deployment state, metrics, and task names can drift, and a successfully trained production model does not make Agriculture analysis available.

Evidence:

- Vision registry/deployment flows persist `backend/modules/vision/models.py::ModelVersion`.
- Agriculture analysis gate and aggregation query `backend/modules/agriculture/models.py::AgricultureModelVersion`.
- No audited code links the two records or promotes a Vision production version into the Agriculture registry.
- The Agriculture record carries model/task lifecycle concerns that overlap Vision’s canonical artifact lifecycle.

Implementation:

1. Write an ADR and schema contract declaring Vision `ModelVersion` the sole owner of artifact URI, integrity hash, training/evaluation provenance, version identity, and candidate/production lifecycle.
2. Replace the duplicate Agriculture artifact record with an agronomic capability release/policy record that references a Vision model-version ID and stores only Agriculture-owned data: canonical capability ID, crop/sensor applicability, thresholds, approval/review status, and effective dates.
3. If existing `AgricultureModelVersion` rows may be persisted, migrate them deterministically: link when artifact/version identity is unambiguous, quarantine ambiguous rows for operator review, and never silently discard production references.
4. Expose a typed read contract returning “available capability + deployed Vision version + evaluated inference profile” without leaking cross-module ORM models.
5. Make production uniqueness database-enforced by tenant/project/capability as appropriate.

Files likely affected: `backend/modules/vision/models.py`; `backend/modules/vision/repository.py`; `backend/modules/vision/services/*`; `backend/modules/agriculture/models.py`; `backend/modules/agriculture/service.py`; new Alembic migration; API schemas; architecture docs; tests.

Acceptance criteria:

- One durable record owns each model artifact and lifecycle fact.
- Deploying an eligible Vision model can make its canonical Agriculture capability available without copying artifact fields.
- Agriculture can resolve the exact model hash/version and inference profile used for every finding.
- Migration preserves or explicitly quarantines all existing rows and supports rollback before destructive cleanup.
- Concurrent deployment cannot create two effective production releases for the same scope.

Tests: Migration upgrade/downgrade on empty and fixture databases; contract tests across both modules; concurrent deployment test; tenant-isolation test; artifact provenance round trip.

Performance target: Capability resolution uses at most one indexed join/query and does not load training artifacts or annotation data.

Dependencies: `AGR-001`. Blocks `AGR-002`, `AGR-003`, and `ML-005`.

Risk: High. This touches persisted governance data and cross-module ownership. Inventory dynamic/API/operational consumers before removing old columns or records.

Size: L.

### AGR-002 — Make analysis requests capability-aware and canonical

Tags: `P0` `agriculture` `api` `frontend` `product-contract`

Problem: The frontend requests a hardcoded broad analysis set, the backend rejects unavailable models, and aliases differ across layers. Users cannot understand what can run or why it cannot.

Evidence:

- Agriculture analysis creation currently sends `quality`, `canopy`, `rows`, `stand_count`, `weed`, `standing_water`, and `crop_health` by default.
- Backend gating treats quality/coverage/RGB quality differently and requires deployed models for the remaining names.
- Service/release code uses variants such as `canopy_cover` and `row_detection`.
- The UI does not derive choices from media type, sensor metadata, crop context, or deployed capability releases.

Implementation:

1. Define a versioned canonical capability enum/catalog with stable IDs, display names, required media/sensor metadata, required model profile, output type, and action relevance.
2. Add a field/mission analysis-readiness endpoint returning capture quality prerequisites, available capabilities, unavailable reasons, selected release IDs, and advanced configuration defaults.
3. Make the UI select only available capabilities, defaulting to the smallest useful set; quality analysis may run independently where valid.
4. Reject unknown aliases at the API boundary after a bounded migration period; normalize persisted legacy names in a migration rather than maintaining permanent alias branches.
5. Persist the resolved capability/release snapshot on the analysis run so later deployment changes do not alter provenance.

Files likely affected: `frontend/src/modules/agriculture/api.ts`; `hooks.ts`; `types.ts`; post-flight components; `backend/modules/agriculture/api.py`; `schemas.py`; `service.py`; capability/release models; migration; contract docs and tests.

Acceptance criteria:

- A user can see which analyses are ready, unavailable, or blocked and a plain-language reason for each.
- The UI never submits an unavailable capability by default.
- Every accepted capability resolves to one canonical ID and immutable release snapshot.
- A quality-only run works without an unrelated ML deployment.
- Legacy persisted aliases are migrated or explicitly reported; no silent remapping remains indefinitely.

Tests: Capability-catalog unit tests; API readiness matrix by media/sensor/model state; frontend selection tests; legacy-name migration test; tenant and authorization tests.

Performance target: Readiness response p95 under 300 ms on a representative tenant fixture, with a bounded query count recorded in tests.

Dependencies: `ML-001`; `AGR-001`.

Risk: Medium. A canonical rename can break persisted/API consumers; use an inventory and migration, not an unbounded compatibility layer.

Size: M.

### VID-001 — Guarantee truthful terminal states and recover stale video jobs

Tags: `P0` `video` `workers` `reliability` `correctness`

Problem: A failed inference job can leave its video asset marked `analyzing`, all frames can fail while the job becomes `completed`, and there is no clear heartbeat/stale-job recovery path.

Evidence:

- The pipeline failure handler updates the job but does not consistently restore the linked video status.
- Per-frame standard-inference exceptions are continued; a run with no successfully processed frames can reach normal completion with zero detections.
- Jobs expose state but no audited lease/heartbeat reconciliation protects worker loss.

Implementation:

1. Define one transactional terminal-state matrix for job and video: completed, failed, cancelled, and retryable/stale.
2. Track attempted, decoded, inferred, failed, and persisted frame counts separately. Treat zero successful inference frames as failure unless the user explicitly ran a validated no-op mode.
3. Record bounded structured failure reasons and stage; do not expose raw local paths or arbitrary exception payloads.
4. Add heartbeat/lease timestamps and a reconciler that marks expired jobs retryable/failed according to retry policy while restoring the video state.
5. Make terminal transitions idempotent and safe under duplicate worker delivery.

Files likely affected: `backend/modules/video_analysis/pipeline.py`; application/service and repository files; VideoJob/VideoAsset models and migration; Celery tasks; schemas; frontend status/error components; tests.

Acceptance criteria:

- Every terminal job has a compatible terminal video state.
- A run where every selected frame fails cannot report success.

### VID-004 — Make detector loading immutable and provenance-verifiable

Tags: `P2` `video` `models` `cache` `provenance` `reliability`

## NOT RECOMMENDED / NOT NOW

- Do not add more Agriculture analysis types until one capability completes the capture-to-reviewed-finding slice with exact provenance.
- Do not synchronize two full model registries with hooks, cron jobs, or copied artifact metadata. Establish one artifact owner and link Agriculture policy.
- Do not split the modules into microservices now. Typed in-process contracts and isolated worker queues solve the demonstrated boundary/scaling problems with less operational risk.
- Do not introduce a generic event bus, repository framework, or plugin architecture solely to decouple three known calls. Use narrow application ports and persisted idempotent stages.
- Do not optimize decoding, batch size, SAHI overlap, precision, or tracking from intuition. Baseline representative GPU/media workloads and correctness first.
- Do not expose detector brand, SAHI slices, thresholds, model IDs, or telemetry tolerance as the default farmer workflow. Keep them in validated release profiles and advanced diagnostics.
- Do not automatically generate or execute chemical/fertilizer prescriptions from RGB detections. Require agronomic validation, supported sensor calibration, explicit approval, and downstream conformance.
- Do not claim accuracy, yield improvement, cost savings, or offline behavior based on competitor marketing or synthetic benchmarks.
- Do not store one crop forever for every detection by default. Decide from evidence-review needs, retention policy, and measured hit rate.
- Do not make WebSockets/SSE a prerequisite merely to replace inefficient polling. Cursor/delta and visibility-gated queries are sufficient first; adopt push only if measured latency/load and existing infrastructure justify it.
- Do not build a native mobile app or force full phone-based precision labeling now. Make field review and core operations responsive; validate whether annotation creation genuinely needs another platform.
- Do not perform a repository-wide formatting/type rewrite while delivering the vertical slice. Enforce focused correctness gates on touched modules and burn down baseline debt in bounded tasks.
- Do not delete apparently unused dependencies, schemas, legacy zones, media manifests, or routes based only on source search. Complete the proof gates in the removal plan.
- Do not retain old and new implementations indefinitely “for safety.” Use metrics, parity tests, a rollback window, and a dated removal gate.

## Implementation quality gates

Every task above is complete only when all applicable conditions hold:

1. Public contracts and persisted data are preserved or migrated explicitly.
2. Tenant/role authorization and audit behavior are tested at the owning boundary.
3. Retry, duplicate delivery, cancellation, timeout, and partial failure behavior are defined for asynchronous work.
4. Tests cover the changed behavior at the lowest useful level plus the relevant vertical contract.
5. Focused lint/type checks, frontend build, migration single-head check, and `git diff --check` pass.
6. Browser-facing changes pass keyboard, focus, label, contrast, responsive, loading, empty, error, and reduced-motion checks where applicable.
7. Performance claims include workload, hardware, dataset/media cardinality, before/after distribution, and correctness comparison.
8. Obsolete paths are removed after migration proof; no unbounded compatibility path is added.
9. Operations receive metrics, bounded logs, recovery/runbook updates, and storage/backup implications.
10. The repository remains in a valid, testable state after each vertical slice.
